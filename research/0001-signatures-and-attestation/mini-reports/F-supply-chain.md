# Area F — Software Supply Chain Attestation

*All dates, versions, RFC numbers and DOIs below were verified this session against primary sources (RFC Editor, NVD, Crossref/OpenAlex, Federal Register API, EUR-Lex/CELLAR, project specification repositories). Nothing is cited from memory.*

---

## 1. The attacks that motivated the field

**SolarWinds / SUNBURST (disclosed 13 Dec 2020).** The decisive case, because every artifact-level control worked. CrowdStrike's analysis of the **SUNSPOT** implant shows it ran *on the build server*: it polled for `MsBuild.exe`, confirmed via the process PEB that the Orion solution was compiling, swapped `InventoryManager.cs` for a backdoored copy, let MSBuild compile it, then restored the original. The resulting `SolarWinds.Orion.Core.BusinessLayer.dll` was signed with SolarWinds' genuine code-signing certificate (revoked 8 Mar 2021). The git repository was never touched; the divergence existed only inside one build machine's working directory, for the duration of one compile. Source review would not have caught it, and signature verification *succeeded*. SolarWinds' SEC Form 8-K (14 Dec 2020) states "fewer than 18,000" customers "may have had an installation... that contained this vulnerability" — an upper bound on exposure, not a count of compromises. **There is no CVE for SUNBURST**; CVE-2020-10148 is a separate Orion API auth bypass tied to SUPERNOVA. The lesson: signing attests *provenance*, not *integrity of build inputs*.

**event-stream (npm, 2018).** A pure authorization failure. The original maintainer handed publish rights to a volunteer who asked by email — Dominic Tarr, in issue #116 on 22 Nov 2018: *"he emailed me and said he wanted to maintain the module, so I gave it to him."* `event-stream@3.3.6` (published 2018-09-09) added `flatmap-stream@0.1.1`, whose AES payload decrypted only when `npm_package_description` equalled "A Secure Bitcoin Wallet" — i.e. inside Copay's release build. BitPay confirmed Copay 5.0.2–5.1.0 affected. Advisory GHSA-mh6f-8j2x-4483; no CVE. Nothing cryptographic was broken: the legitimate publisher published.

**xz-utils (2024).** CVE-2024-3094, published 2024-03-29, CVSS 3.1 base **10.0 CRITICAL** (`AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H`). Andres Freund found it while chasing sshd CPU anomalies. Crucially, the activation glue — `build-to-host.m4` — existed **only in the release tarballs, not in git**; the payload itself sat in git disguised as corrupt-input test fixtures. Tukaani's own statement: *"XZ Utils 5.6.0 and 5.6.1 release tarballs contain a backdoor. These tarballs were created and signed by Jia Tan."* Tags v5.6.0 (2024-02-24) and v5.6.1 (2024-03-09) were both cut by "Jia Tan", who first patched xz on 2021-10-29 and gained release authority with v5.4.2 on 2023-03-18 — roughly **17 months from first contact to signing authority**, aided by sockpuppets ("Jigar Kumar", "Dennis Ens") pressuring the maintainer about bus factor. This attacks the *distribution* of authority, and shows source-vs-artifact divergence as a first-class threat.

**Typosquatting.** Ohm et al. (DIMVA 2020) curated 174 malicious packages (Nov 2015–Nov 2019; 62.6% npm, 16.1% PyPI, 21.3% RubyGems) and found **61% leveraged typosquatting**, mean Levenshtein distance to target 2.3. Vu et al. (EuroS&PW 2020) measured the same on PyPI. This is a *naming* attack — no signature, no build, no provenance claim is falsified. It is entirely outside what attestation formats express.

## 2. in-toto

Torres-Arias, Afzali, Kuppusamy, Curtmola and Cappos (USENIX Security 2019) introduced the **layout** — signed by the project owner, who the paper calls "the foundation of trust" — enumerating *steps*, the `pubkeys` (KEYIDs) authorized to sign each step's **link** metadata, a `threshold`, and artifact rules (`MATCH`, `CREATE`, `MODIFY`, `DELETE`, `ALLOW`, `DISALLOW`, `REQUIRE`) that chain steps by material/product flow. Evaluated against 30 historical compromises, the three deployments covered 83–100%.

The **in-toto Attestation Framework** (spec v1.0 released 2023-03-22; current v1.2.0, 2026-03-18) generalized this into four layers. **Statement**: `_type: "https://in-toto.io/Statement/v1"`, `subject` (array of ResourceDescriptors), `predicateType`, `predicate`. **Predicate**: type-specific metadata. **Envelope**: DSSE, with `payloadType` of `application/vnd.in-toto+json`. **Bundle**: JSON Lines, media type `application/vnd.in-toto.bundle`, order-independent — and explicitly *"the Bundle is not authenticated as a whole,"* so attestations can be deleted, replayed or injected undetected. in-toto graduated CNCF on 2025-02-10.

## 3. DSSE — and the refusal to canonicalize

DSSE began as in-toto Enhancement ITE-5 (repo initial commit Sept 2020). PAE is:

```
PAE = "DSSEv1" SP LEN(type) SP type SP LEN(body) SP body
```

`LEN` is ASCII decimal, no leading zeros; SP is 0x20. The envelope is `{payload, payloadType, signatures[{keyid, sig}]}`, and `keyid` is *"an optional, unauthenticated hint... MUST NOT be used for security decisions."*

The design rationale in `background.md` is a substantive position, stated precisely. Canonical JSON has **one practical and two theoretical problems**: (1) practical — *"It requires the payload to be JSON or convertible to JSON"*; (2) theoretical — *"Two semantically different payloads could have the same canonical encoding"*; (3) theoretical — *"It requires the verifier to parse the payload before verifying, which is both error-prone—too easy to forget to verify—and an unnecessarily increased attack surface."* The conclusion: *"The preferred solution is to transmit the encoded byte stream exactly as it was signed, which the verifier verifies before parsing."*

This inverts the usual order of operations. The verification steps are normative: verify the signature over `PAE(payloadType, body)`; **reject if `payloadType` is unsupported; only then parse**. The parser is downstream of the signature check, so a malformed or hostile payload never reaches it unauthenticated. Signing `payloadType` inside PAE also closes a cross-format confusion attack: without an authenticated context indicator, a signer could be induced to produce a CBOR message saying X that a verifier interprets as protobuf saying Y. The requirements are stated as `SHOULD avoid depending on canonicalization for security` and `SHOULD NOT require the verifier to parse the payload before verifying` — a deliberate refusal to make semantic equivalence a security primitive.

## 4. SLSA

v1.0 (2023-04-19), v1.1 (2025-04-21), **v1.2 current (2025-11-24)**, which added the Source track. Build levels: L0 (nothing), L1 (provenance exists), L2 (hosted platform, signed provenance), L3 (hardened — isolation between builds, no build access to signing secrets, no cache poisoning across runs). Source track L1–L4 (version controlled → history & provenance → continuous technical controls → two-party review); SLSA deliberately *"leaves source provenance attestations undefined."*

The **Provenance** predicate (`https://slsa.dev/provenance/v1`) carries `buildDefinition{buildType, externalParameters, internalParameters, resolvedDependencies}` and `runDetails{builder{id}, metadata, byproducts}`. The **VSA** (`https://slsa.dev/verification_summary/v1`) carries `verifier`, `timeVerified`, `resourceUri`, `policy`, `verificationResult` (PASSED/FAILED), `verifiedLevels` — letting consumers delegate verification to a trusted party.

## 5. Sigstore

Newman, Meyers and Torres-Arias, *Sigstore: Software Signing for Everybody*, ACM CCS 2022, pp. 2353–2367 (DOI 10.1145/3548606.3560596). **Fulcio** issues X.509 certificates valid for **10 minutes**, binding an ephemeral key to an OIDC identity placed in the SAN. **Rekor** is an append-only Merkle transparency log with signed tree heads; Rekor v2 went GA in Oct 2025 on Trillian-Tessera tiles. **Cosign** orchestrates: generate in-memory keypair → OIDC → Fulcio cert → sign → log to Rekor. The Sigstore trust root is distributed via TUF.

## 6. IETF SCITT

**RFC 9943**, *An Architecture for Trustworthy and Transparent Digital Supply Chains* — Birkholz, Delignat-Lavaud, Fournet, Deshpande, Lasker — **Proposed Standard, IETF stream, June 2026** (verified). Terms: an **Issuer** signs a **Statement** about an **Artifact** to produce a **Signed Statement**; a **Transparency Service** applies a **Registration Policy** and appends to a verifiable data structure, returning a **Receipt** (per **RFC 9942**, *COSE Receipts*, Steele/Birkholz/Delignat-Lavaud/Fournet); Signed Statement + Receipt = **Transparent Statement**. **SCRAPI** (`draft-ietf-scitt-scrapi-11`, revised 2026-06-26) is in the RFC Editor queue.

## 7. TUF and Notary

Samuel, Mathewson, Cappos and Dingledine, CCS 2010, pp. 61–72 (DOI 10.1145/1866307.1866315). TUF is the field's strongest authorization model: four top-level roles (**root**, **targets**, **snapshot**, **timestamp**), each with a **threshold** — *"a positive integer number of keys (>=1) of that role whose signatures are required"* — and **delegated targets** roles scoped by path patterns or hash prefixes, with **terminating vs. non-terminating** delegation semantics. Root delegates trust to keys for every other role. Spec v1.0.36 (2026-08-05); CNCF graduated 2019-12-18, the first specification and first security project to do so. Notary v1 was TUF-based (Docker Content Trust); the Notary Project (CNCF incubating, accepted 2017-10-24) and its Notation tooling are built around trust stores and trust policies rather than TUF metadata.

## 8. SBOM formats — what they prove vs. claim

**SPDX** is **ISO/IEC 5962:2021**, which standardizes SPDX **2.2.1**, not 3.x. SPDX 3.0 shipped April 2024, 3.0.1 on 2024-12-17. **CycloneDX** is stewarded by OWASP and standardized at Ecma TC54 as **ECMA-424**: 1st edition June 2024 (= v1.6), **2nd edition 2025-12-10 (= v1.7)**. CycloneDX carries VEX, CBOM, ML-BOM, HBOM, and **CDXA** (attestations: claims, evidence, testimony). NTIA's *Minimum Elements* (2021-07-12) defined seven data fields plus automation support (SPDX, CycloneDX, SWID) and six practices; it has been **superseded by CISA's "2026 Minimum Elements," 2026-07-29**.

An SBOM is a **claim about composition, asserted by whoever generated it**. Unsigned, it proves nothing. Wrapped in a DSSE envelope as an in-toto predicate, it proves only that a particular key asserted that component list for that artifact digest — not that the list is complete, not that it was derived from the actual build, and not that the asserter was entitled to speak for the artifact. An SBOM generated by post-hoc binary analysis and one emitted by a hermetic builder are indistinguishable at the envelope layer. Note also that xz's backdoor would appear in **no** SBOM: the component list was correct; the *bytes of that component* differed from its source.

## 9. Regulation

**EU CRA, Regulation (EU) 2024/2847** (OJ L, 2024/2847, 20.11.2024). Article 71: entry into force **10 Dec 2024**; general application **11 Dec 2027**; **Article 14** (reporting actively exploited vulnerabilities via the ENISA platform) from **11 Sep 2026**; **Chapter IV** (Arts. 35–51, notification of conformity assessment bodies) from **11 Jun 2026**. The SBOM obligation is **Annex I, Part II, point (1)**: manufacturers must *"identify and document vulnerabilities and components... including by drawing up a software bill of materials in a commonly used and machine-readable format covering at the very least the top-level dependencies."* No format is named — Article 13(24) lets the Commission specify one later by implementing act. Annex VII puts the SBOM in the technical documentation, disclosable to market surveillance authorities on reasoned request; **Annex II point 9 makes disclosure to users optional**. So the CRA mandates an SBOM's *existence*, one level deep, in an unnamed format, primarily for regulators.

**US: EO 14028** (signed 2021-05-12, 86 FR 26633), Section 4 "Enhancing Software Supply Chain Security" — §4(e)(vii) SBOM provision, §4(e)(ix)–(x) attestation to secure development practices and to open-source provenance, §4(f) the NTIA minimum-elements mandate. **EO 14028 has not been revoked or textually amended.** But the machinery moved: **EO 14144** (2025-01-16, 90 FR 6755) §2 directed FAR language requiring *machine-readable* secure-development attestations plus validating artifacts into CISA's RSAA — and **EO 14306** (2025-06-06, 90 FR 24723) **struck EO 14144 §2(a)–(b)**, replacing the attestation-validation program with a NIST/NCCoE industry consortium producing SSDF guidance. The word "attestation" does not appear in EO 14306. **NIST SP 800-218 v1.1** (Feb 2022) remains current; SP 800-218A (2024-07-26) is final but its originating mandate (EO 14110) was revoked by EO 14148.

## 10. The analytical core: strong deployment, weak authorization

The honest assessment is that this domain has built an excellent **evidence layer** and almost no **entitlement layer** — and, uncomfortably, the projects say so themselves.

**Almost every scheme takes the authorization decision as an input.** The in-toto Attestation Framework's own validation model takes `recognizedAttesters` — a collection of `(name, publicKey)` pairs — as a *parameter*, and emits `attesterNames` as output *"to be fed into policy engine."* The framework has no notion of which attester may speak about which subject or predicate type. SLSA is equally explicit: *"Consumers MUST accept only specific signer-builder pairs"* and `builder.id` *"MUST reflect the trust base that consumers care about"* — but the signer→builder mapping lives nowhere in the format. SLSA's "forming expectations" section offers three models (trust on first use, defined by producer, defined in source) and mandates none. Sigstore's threat model states that verifying a keyless signature *"does not guarantee that the signer should be able to authenticate... or that the signer should have signed the given message"*; verifiers *"must establish their own policy determining which identities are permitted to sign a given software artifact."* This is enforced concretely: `cosign verify` refuses keyless verification without `--certificate-identity` and `--certificate-oidc-issuer` — the expected identity is a *command-line argument*, supplied out-of-band by whoever runs the verifier. SCITT is the bluntest: *"Authentication and authorization are implementation specific and out of scope of the SCITT architecture,"* and *"Relying Parties can use the history of registered Signed Statements to decide which Issuers they choose to trust. This decision process is out of scope of this document."*

**Two genuine exceptions, and they are the oldest ideas in the field.** **TUF** does express scoped delegation properly: root delegates to roles with thresholds; targets delegates to sub-roles scoped by path pattern, with terminating and non-terminating semantics, so "who may sign for `django/*`" is a first-class, verifiable, revocable statement. **in-toto's layout** likewise binds specific KEYIDs to specific steps with thresholds and artifact-flow rules — real scoped delegation. But both bottom out in an assumed root. The in-toto paper says so directly: *"We assume that the public keys of project owners are known to the verifiers"* and *"in-toto will not mandate how trust is bootstrapped."* TUF's root role is the out-of-band anchor by construction. So the answer is not "nobody does delegation" — it is that delegation exists *below* the root and nothing standardizes the root, and the newer, far more widely deployed layer (in-toto attestations, SLSA, DSSE, Sigstore) dropped the delegation machinery and kept only the envelope.

**SCITT is the interesting middle case and deserves credit.** It mandates that a Registration Policy *exist* (*"To enable auditability, TSs MUST maintain Registration Policies"*), that trust anchors be maintained, and — importantly — that *"Registration Policies and trust anchors MUST be made Transparent and available to all Relying Parties of the TS by Registering them as Signed Statements on the VDS,"* with the TS applying the most recently committed policy. That makes the authorization decision *auditable and versioned*, which is more than anyone else offers. But it standardizes only the obligation, not the language: *"This specification leaves implementation, encoding, and documentation of Registration Policies and trust anchors to the operator of the TS."* Policy is transparent but not interoperable.

**Where authorization actually lives today is the registry, not the attestation.** PyPI Trusted Publishing binds a specific OIDC identity (repo + workflow + environment) to permission to publish a specific project, minting a 15-minute project-scoped token. That is real scoped delegation — and it is implemented by the package index, out of band from every format described above. The ecosystems solved the problem the formats declined to.

**The 2026 Mini Shai-Hulud attack is the empirical proof.** On 11 May 2026, attackers compromised 84 npm artifacts across 42 `@tanstack` packages (spreading to 170+ across other namespaces) by chaining a `pull_request_target` misconfiguration, GitHub Actions cache poisoning, and OIDC token extraction from runner memory. The resulting packages carried **cryptographically valid** provenance attestations that accurately named the correct builder, repository, workflow and ref — signed through Sigstore with the legitimate OIDC token. SLSA's own write-up concedes the point: *"SLSA provenance records evidence. It answers 'what happened?' Policy and verification answer 'was that good enough?'"* and *"An 'expected builder' check would have passed, because the pipeline was legitimate; it was the code running inside it that was not."* Every "who signed this" question was answered correctly, and the answer was useless.

**Assessment.** in-toto and SLSA are excellent *provenance* formats and poor *authorization* formats, by design and by admission — they are evidence grammars deliberately agnostic about policy. That agnosticism is precisely why adoption succeeded: a format that made no trust commitments could be adopted by GitHub, npm, PyPI, Google and Debian simultaneously. But it means the field has industrialized the production of signed statements while leaving "who was entitled to say that" to a `--certificate-identity` flag, a registry configuration page, or a policy engine nobody has standardized. The three plausible recovery paths — TUF-style delegation reapplied to attestation subjects (gittuf, NDSS 2025, does exactly this for Git), SCITT registration policies given an interoperable language, or VSAs as recursive delegated authority — all exist. None has consolidated. Regulation compounds the gap rather than closing it: the CRA mandates an SBOM's existence but no format, no depth beyond top-level, and no signer; and the one US instrument that would have required *machine-readable attestations with validating artifacts* (EO 14144 §2(a)–(b)) was struck by EO 14306 in June 2025.
